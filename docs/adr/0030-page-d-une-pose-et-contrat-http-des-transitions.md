# 0030. Page d'une pose et contrat HTTP des transitions

- Statut : accepté
- Date : 2026-11-13
- Complète : [0007](0007-contrat-http-et-persistance-modulaire.md), [0018](0018-contrat-http-de-contribution.md), [0024](0024-version-d-une-pose-publiee.md), [0027](0027-file-de-validation-et-mes-propositions-heterogenes.md), [0028](0028-transition-publiee-et-proposition-de-transition.md)

## Contexte
La page d'une pose (story 7, C1 à C12) présente, pour tout visiteur, la pose et deux listes : les transitions qui en partent et celles qui y arrivent, chacune avec l'autre pose (nom actuel, lien), son nom éventuel, ses difficultés et sa description, dans l'ordre du catalogue sur l'autre pose puis sur le nom, les transitions sans nom en premier. Le site doit distinguer une pose introuvable d'un AcroFunJam injoignable et d'une pose sans transition. Côté Contribution, une transition se propose, se décide et se suit comme les autres propositions (ADR 0027).

## Options envisagées
1. **Enrichir `GET /catalog/poses/{id}`** des deux listes : une seule ressource, une seule requête, un seul 404 ; le formulaire de modification (story 6) reçoit des données dont il n'a pas besoin.
2. **`GET /catalog/poses/{id}/transitions`** à côté de la pose : deux requêtes et deux états d'erreur à combiner par le site.
3. **Ressource dédiée `GET /catalog/pose-pages/{id}`** : forme taillée pour l'écran, mais une seconde représentation de la même pose.

## Décision
**Option 1.**
- `GET /catalog/poses/{id}` (anonyme) : `200 { "id", "name", "baseDifficulty", "flyerDifficulty", "canStartFlow", "canEndFlow", "version", "transitionsFrom": [ T ], "transitionsTo": [ T ] }`, où `T = { "id", "otherPose": { "id", "name" }, "name": string | null, "baseDifficulty", "flyerDifficulty", "description": string | null }` ; `otherPose` est la pose d'arrivée dans `transitionsFrom`, la pose de départ dans `transitionsTo` ; une washing machine figure dans les deux listes avec `otherPose.id` égal à `id` (le site en déduit « (même pose) ») ; listes vides `[]` ; `404 catalog.pose-not-found`. Ajout compatible : le formulaire de modification ignore les deux listes.
- Lecture : query `GetPosePage` du Catalogue, la pose lue par `IPoseRepository.GetById`, puis ses transitions par le port de lecture `IPoseTransitionsReader` (projection directe avec le nom actuel de l’autre pose par jointure dans le schéma `catalog`). La lecture d’une pose pour la modifier (ACL `CatalogPoses.Find`, story 6) passe aussi par `GetPosePage` : deux lectures de transitions inutiles dans ce cas, coût accepté. `OtherPoseResponse` (Catalogue) et `PoseReferenceResponse` (Contribution) ont la même forme mais restent distincts : deux langages publiés, ordre appliqué par le comparateur du domaine `LinkedTransitionsOrder` (nom de l'autre pose dans l'ordre du catalogue, puis nom de la transition, sans nom en premier, ADR 0017). L'ordre est total grâce à l'unicité de la place (ADR 0029). `GetPublishedPose` (story 6) est remplacée par `GetPosePage`.
- Contribution (policy `CanPropose` pour proposer et suivre, `CanValidate` pour décider), dans le style de l'ADR 0027 :
  - `POST /contribution/transition-proposals` : corps `{ "fromPoseId", "toPoseId", "name"?, "baseDifficulty", "flyerDifficulty", "description"? }` ; réponse `201 { "id", "status": "pending" | "accepted", "fromPose": { "id", "name" }, "toPose": { "id", "name" }, "name": string | null, "baseDifficulty", "flyerDifficulty", "description": string | null }` (valeurs normalisées, noms actuels des poses) ;
  - `POST /contribution/transition-proposals/{id}/acceptance` : corps `{ "name"?, "baseDifficulty"?, "flyerDifficulty"?, "description"?, "message"? }` (absent ou `null` : inchangé ; `""` ou espaces pour le nom ou la description : retiré) ; réponse `200 { "id", "status": "accepted", "adjusted", "fromPose", "toPose", "name", "baseDifficulty", "flyerDifficulty", "description" }` (valeurs retenues) ;
  - `POST /contribution/transition-proposals/{id}/rejection` : `{ "reason" }` → `200 { "id", "status": "rejected" }` ;
  - `GET /contribution/validation-queue` : nouveau `kind: "transition-proposal"` : `{ "kind", "id", "fromPose": { "id", "name" }, "toPose": { "id", "name" }, "name", "baseDifficulty", "flyerDifficulty", "description", "contributor": { "email", "isYou" }, "submittedAt" }` ; `/count` compte aussi les transitions ;
  - `GET /contribution/my-proposals` : nouveau `kind: "transition-proposal"` : `{ "kind", "id", "status", "fromPose", "toPose", "name", "baseDifficulty", "flyerDifficulty", "description", "submittedAt", "decidedAt", "adjustments": null | { "name": null | { "proposed": string | null, "retained": string | null }, "baseDifficulty": null | { "proposed", "retained" }, "flyerDifficulty": null | { … }, "description": null | { "proposed": string | null, "retained": string | null } }, "message", "reason" }` (transition retenue si acceptée, proposée sinon ; jamais le validateur).
- Codes d'erreur : 400 `contribution.from-pose-required`, `contribution.to-pose-required`, `transition.name-without-letter-or-digit`, `transition.name-too-long`, `transition.description-too-long`, `pose.base-difficulty-required`, `pose.flyer-difficulty-required`, `pose.unknown-difficulty-level`, et ceux des décisions (story 4) ; 404 `contribution.from-pose-not-found`, `contribution.to-pose-not-found`, `contribution.proposal-not-found` ; 409 `contribution.transition-name-already-in-catalog`, `contribution.transition-name-already-pending`, `contribution.unnamed-transition-already-in-catalog`, `contribution.unnamed-transition-already-pending`, `contribution.proposal-already-decided` ; 422 `contribution.adjustment-note-without-adjustment` ; 401 et 403 comme les autres propositions.
- Le site ne lit aucune liste de transitions pour proposer : la pose de départ et la liste déroulante de la pose d'arrivée viennent de `GET /catalog/poses` (poses publiées seulement) ; une pose de départ absente de cette liste donne « Cette pose n'est plus dans le catalogue. ».

## Conséquences
- Le formulaire de modification charge quelques transitions inutiles : coût jugé négligeable ; à revoir si une pose en accumule beaucoup (pagination, ou option 3).
- Le web et le futur mobile lisent la même page en une requête ; le site distingue `404` (« Pose introuvable »), erreur réseau (« Réessayer ») et listes vides (messages par section).
- Un client doit tolérer un `kind` inconnu (ADR 0027) : le site déjà déployé affiche une transition comme « site à mettre à jour » tant qu'il n'est pas livré, d'où une livraison de l'API et du site dans la même mise en production.
